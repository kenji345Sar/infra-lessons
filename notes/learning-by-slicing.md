# 設定とコマンドの「正体」を知るための 4 つの切り方

インフラ題材では「設定ファイルを書いた」「コマンドが通った」で終わりがちで、その下で何が起きているかが見えにくい。「動いた、でも正体がわからない」という状態は、**切り方が 1 つしかない** から起きる。

この note は、その「切り方」を 4 つ持つことで、同じ題材を多面的に観察できるようにする方針メモ。

## 前提: 設定とコマンドの位置付け

「設定」と「コマンド」は、コードそのものではなく、**既存のコードに対する操作面**:

- **設定**（例: `nginx.conf`）= 既存のコード（nginx の実装）が読み取る **テキスト入力**。挙動を **選ぶ** もの
- **コマンド**（例: `curl --cert ...`）= 既存のバイナリ（curl 等）を **引数つきで起動** する命令

両方とも「コードに対する操作面」だが、役割と動きが違う:

| | 役割 | 動き |
|---|---|---|
| 設定 | コードの **動き方を選ぶ**（スイッチ・パラメータ） | 静的（事前に決めておく） |
| コマンド | コードの **実行を起こす**（トリガー） | 動的（その場で発火） |

つまり、設定もコマンドも「コードに何をさせるか」を指示するもので、コード本体（D）は別にある。この前提があると、以下の 4 切りで C（設定の意味）と D（実装）を分けて扱う理由が腑に落ちる。

## 「正体 = コード」ではない

「正体を知る = コードを書く」と思いがちだが、それは 4 つある切り方の **ひとつ** にすぎない。

| 切り方 | 何を見るか | ツール / やり方 |
|---|---|---|
| A. **プロトコル** | RFC で決まっている「やりとりの順番と内容」 | RFC / シーケンス図を書く |
| B. **パケット** | 実際にネットワークに流れたバイト列 | `tcpdump` / Wireshark |
| C. **設定の意味** | 1 行のディレクティブが裏で何のスイッチを立てているか | 設定をオン/オフして挙動の差を見る |
| D. **実装 (= コード)** | その機能を自分の手で書き直す | Python の `socket` + `ssl` などで再実装 |

D だけに偏ると「なぜそのコードになっているか」が見えない。逆に A・B・C を抜くと「設定の意味」が宙に浮く。

### 各観点が指す実体

抽象を実体に対応づけると次の通り:

- **A. プロトコル** → RFC に書かれているルール
- **B. パケット** → そのルールに従って実際に流れるデータ
- **C. 設定の意味** → nginx / curl 等でどの機能を ON / OFF するか
- **D. 実装** → OpenSSL / nginx / curl 等のコード

## 補足: A と D は「ルール」と「ルールを動かすもの」

4 切りの中で、A（プロトコル）と D（実装）は紛らわしいので位置関係をはっきりさせておく。

- **A. プロトコル** = 人間どうしの **合意 / ルール**。物理的実体はない。RFC（例: RFC 8446 = TLS 1.3）はその合意を書き写した文書
- **D. 実装** = その合意に従って動く **コード**（OpenSSL、nginx、Python の `ssl` モジュール）

A を見るとは「**RFC やシーケンス図を読む**」こと。D を見るとは「**コードを書く / 読む**」こと。同じ TLS でも、観察対象がルール側か実装側かで切り方が変わる。

C（設定の意味）は **D の上に乗っかった操作**。`ssl_verify_client on` という設定は、D（nginx の実装）が露出させているスイッチを操作している。C を独立した切り方として持つ理由は、**設定 1 行で挙動を変えられる粒度** が、コードを書き直すより速く「正体」に近づける場面が多いから。


## step-05〜06 を例にする

`https://cds01/` への `curl --cert ...` 1 発で 200 OK が返るところまで作ったが、「正体」を見るには 4 切り全部を当てる:

| 切り方 | step-05〜06 への当て方 |
|---|---|
| A. プロトコル | TLS ハンドシェイクのメッセージ列を図にする（ClientHello / ServerHello / Certificate / CertificateRequest / Finished …） |
| B. パケット | `sudo tcpdump -i any -w cap.pcap port 443` で取って Wireshark で開く。`ssl_verify_client on` の有無でパケットがどう変わるか比較 |
| C. 設定の意味 | `ssl_verify_client on` を外してみる → クライアント証明書なしでも通るようになる、で 1 行の働きを確定させる |
| D. 実装 | Python `socket` + `ssl.SSLContext` で同じことを 15 行ぐらいで書く（鍵・証明書は step-04 の成果物を流用） |

## なぜ 4 切りが効くのか

- **A だけ** → 仕様はわかるが、実物が動いているか保証されない
- **B だけ** → 実物は見えるが、なぜそうなっているか説明できない
- **C だけ** → 「動いた / 動かない」しかわからず、内部の仕組みは見えない
- **D だけ** → 自分のコードは読めるが、既製ソフト（nginx 等）の挙動と一致している保証がない

4 つを行き来すると、「**設定 → プロトコル → パケット → 実装**」が同じものを別角度から指していると確認でき、これが「正体がわかった」状態になる。

## 学習が止まったときの使い方

「設定を書いて、コマンドを叩いて、動いた。でも腑に落ちない」と感じたら、止まっている切り方を切り替える:

1. 今やったのが C（設定）だけ → A（プロトコル図）か B（tcpdump）に進む
2. プロトコル図を描いても実感がない → B（実物のパケット）に進む
3. パケットを見ても抽象的すぎる → D（最小コードで再実装）に進む
4. D で書いたが、既製ソフトと挙動が違う気がする → A に戻って RFC で答え合わせ

「**質問の切り口が決まらないと、答えも返ってこない**」のは、この 4 つのどれで聞いているか決まっていないから。切り方を 1 つ選んでから掘る。
