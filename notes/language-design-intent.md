# 言語の出自と用途の地図

「PHP は Web に強い」「Rust はマイクロサービス向け」── そう聞くが、本当に **そのために作られた** のか? **結果としてそこで使われている** のか? この区別を持っていないと、技術選定や SD 連載の読み解きで判断を間違える。

この note は、主要言語の **本来の設計目的** と、**実際に使われている領域** を分けて整理する。

## 「何のために作られた」と「何に使われている」を分ける

| 言語 | 設計の本来の目的 | 結果としてよく使われる領域 |
|---|---|---|
| **PHP** | **Web アプリ専用** に作られた | Web（CMS、業務 Web アプリ、API）|
| **JavaScript** | **ブラウザ内** で動かす言語として作られた | フロント + バックエンド（Node.js）+ デスクトップ（Electron）|
| **Java** | **「Write once, run anywhere」**のクロスプラットフォーム言語 | エンタープライズ Web、Android、ビッグデータ |
| **C#** | **.NET 上の汎用言語**（Windows 出自） | デスクトップ、Web、ゲーム（Unity）、クラウド |
| **Python** | **可読性の高い汎用スクリプト言語** | スクリプト、データサイエンス、Web、AI/ML |
| **Ruby** | **プログラマの幸福**を重視した汎用スクリプト言語 | Web（Rails）、自動化 |
| **Go** | Google の **大規模システム開発の生産性** 向上 | サーバ、CLI、コンテナ・クラウド基盤 |
| **Rust** | **メモリ安全な C/C++ の代替**（システム言語）| OS、ブラウザエンジン、組み込み、マイクロサービス |
| **C** | UNIX を書くために作られた **システム言語** | OS、組み込み、ドライバ、低レイヤ |
| **C++** | C にオブジェクト指向を足した **システム言語** | ゲームエンジン、ブラウザエンジン、金融、組み込み |
| **Kotlin** | **Java の置き換え**（特に Android）として JetBrains が作成 | Android、サーバサイド、KMP |
| **Swift** | **Objective-C の置き換え**として Apple が作成 | iOS / macOS アプリ |

## 「○○に強い」と感じる理由は出自で決まる

| 言語 | 「○○に強い」と感じる理由 |
|---|---|
| PHP は Web に強い | **元々そう作られた** から（HTML 埋め込み、`$_GET` / `$_POST` 等の組み込み） |
| C# は Windows に強い | Microsoft 製で、Windows 用ライブラリ（WPF / WinForms）が充実しているから |
| Rust はマイクロサービスに使われる | メモリ安全 + 並行処理 + Result 型 が **結果的に** マイクロサービスに刺さった |
| Go はクラウド基盤に使われる | 静的バイナリ + 軽量並行 + 速いコンパイル が **結果的に** Docker / Kubernetes に刺さった |

「**本来の目的**」と「**現実の主戦場**」が一致する言語（PHP、JavaScript）と、ずれている言語（Rust、Go）がある。**「Rust はマイクロサービスのために作られた」と言うと歴史的に誤り**。本来の目的は C/C++ の代替。

## ケーススタディ: C# / .NET / ASP.NET Core の階層

「C# は HTTP プロトコルに特化したものもある」のような表現は、**.NET と C# と ASP.NET Core を混同** していることが多い。以下が正確な関係:

### 三者の役割

| | 何 | 実装言語 |
|---|---|---|
| **.NET**（旧 .NET Core） | **ランタイム + 標準ライブラリ**。言語ではない | ランタイム本体は **C++**、標準ライブラリは **C#** |
| **C#** | **プログラミング言語**。.NET 上で動く | — |
| **ASP.NET Core** | .NET 上で動く **Web フレームワーク**（ライブラリ） | **C#** で書かれている |

### スタック構造

```
[ ユーザーが書く C# コード ]
        │ ASP.NET Core の API を呼び出す
        ▼
[ ASP.NET Core ライブラリ ]   ← C# で書かれている
   ├── Kestrel (HTTP サーバ)
   ├── ルーティング
   └── ミドルウェア
        │ .NET の API を使う
        ▼
[ .NET 標準ライブラリ (BCL) ]   ← C# で書かれている
        │
        ▼
[ .NET ランタイム (CLR) ]   ← C++ で書かれている（JIT、GC、型システム）
        │
        ▼
[ OS (Windows / Linux / macOS) ]
```

### 混乱しやすい誤解

| よくある誤解 | 正しくは |
|---|---|
| 「.NET は言語」 | ✗ .NET は **ランタイム + ライブラリ**。言語は **C#** / F# / VB.NET |
| 「ASP.NET Core は Windows 用」 | ✗ ASP.NET Core は **クロスプラットフォーム**（Linux / macOS / Windows）。混同されやすい古い ASP.NET Framework は Windows 専用 |
| 「C# は ASP.NET Core の上で動く」 | ✗ C# は **「.NET ランタイム上で動く」**。ASP.NET Core は C# が **使うライブラリ**（「上で動く」関係ではない） |
| 「ASP.NET Core は HTTP に特化した実装」 | △ ASP.NET Core は **HTTP 対応の Web フレームワーク**。「HTTP プロトコルの実装そのもの」ではなく、HTTP を扱う上の層 |

### 正しい関係（一文で）

> **C# 言語で書いたコードが、ASP.NET Core という Web フレームワーク（C# 製）を呼び出し、それが .NET ランタイム（C++ 製）上で動いて HTTP リクエストを処理する。**

これが Windows でも Linux でも macOS でも同じように動く。

### ASP.NET の歴史的混乱

- **ASP.NET Framework**（古い、〜 2016 頃）: Windows + IIS 専用。**ここが「Windows 専用」のイメージの源**
- **ASP.NET Core**（新しい、2016〜）: クロスプラットフォーム。**Kestrel という独自 HTTP サーバ** 内蔵
- 現在「ASP.NET」と言うときは、新規開発はほぼ ASP.NET Core を指す

## 同じパターン: 他言語スタックの階層

ASP.NET Core の混乱は、**他の言語スタックでも同じパターン** で起こる:

| 言語 | スタック例 |
|---|---|
| Python | `Python 言語 → Flask / Django（フレームワーク）→ CPython（ランタイム）→ OS` |
| Java | `Java 言語 → Spring Boot（フレームワーク）→ JVM（ランタイム）→ OS` |
| Node.js | `JavaScript 言語 → Express（フレームワーク）→ V8 + libuv（ランタイム）→ OS` |
| PHP | `PHP 言語 → Laravel（フレームワーク）→ PHP 処理系（Zend Engine 等）→ OS` |
| Go | `Go 言語 → Gin / Echo（フレームワーク）→ Go ランタイム → OS` |

**言語 / フレームワーク / ランタイム / OS** が **4 つの別の層** であり、混同しないことが重要。

## なぜこの地図が重要か

1. **技術選定**: 「Web なら PHP、マイクロサービスなら Rust」のような短絡を避けられる
2. **SD 連載の読解**: 「この記事は **どの層** の話か」を見極められる（言語 / フレームワーク / ランタイム / OS）
3. **アーキテクチャ理解**: 階層が見えれば、トラブルが起きたとき **どの層を疑うか** の判断ができる
4. **学習計画**: 「○○を学ぶ」と言ったときに、**どの層を学ぶのか** を明確にできる

## まとめ

- 言語は **「何のために作られたか」** と **「何に使われているか」** を分けて見る
- Rust や Go のように **本来の目的とずれた領域で支持される** 言語もある
- C# / .NET / ASP.NET Core のように **「言語 / ランタイム / フレームワーク」が別物** なのに名前で混乱しやすい例がある
- 階層を **「言語 → フレームワーク → ランタイム → OS」** で並べ替えると、どの言語スタックでも同じ構造に整理できる
