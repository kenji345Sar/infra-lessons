# アプリ層と インフラ層 の対比

同じ「サーバとクライアント」という言葉で違うものを指してしまうので、レイアごとに整理する。後で全プロジェクト俯瞰するときの軸の一つ。

## 出てくるプロジェクト

| プロジェクト | レイア | 何をやっている |
|---|---|---|
| [http-from-scratch](../../http-from-scratch/) | アプリ層 | Python のソケットから HTTP を素手で組み立てる |
| [security-lessons](../../security-lessons/) | アプリ層（〜認証層） | XSS / CSRF / SQLi など Web アプリの脆弱性を再現・修正 |
| [infra-lessons](../) | OS / インフラ層 | VM・OS・ネットワーク・証明書の構築運用 |

## 同じ言葉で違うものを指している

「サーバ」「クライアント」「TLS」は両方のレイアに出てくるが、意味する **物** が違う。

| | アプリ層 (http-from-scratch / security-lessons) | OS / インフラ層 (infra-lessons) |
|---|---|---|
| 「サーバ」とは | `server.py` などのプロセス | `cds01` という OS そのもの（VM） |
| 「クライアント」とは | `client.py` などのプロセス | `client` という別の OS（別の VM） |
| 物理的にどう分けている？ | 同じ Mac 上で別プロセス | 別の OS が動く別の VM |
| OS は誰のもの？ | Mac の macOS（プロセスが借りているだけ）| 各 VM が自分の Ubuntu を持つ |
| ネットワーク | localhost (127.0.0.1) のループバック | 仮想ネットワーク上の異なる IP |
| 設定の対象 | コードの変数・引数 | OS のファイル (`/etc/hosts`, `/etc/nginx/...`)・サービス (systemd, nginx) |
| TLS の有無 | あっても自作・限定的 | OS の nginx + OS の証明書ストアで本物 |

## 「OS が見えなかった」のはなぜか

アプリ開発では OS は **「Python / Node が動いてくれる土台」** として透明になっている。プロセスを起動すれば、メモリ・ファイルディスクリプタ・ソケットは OS が勝手に用意する。アプリ開発者は普通そこを意識しない。

インフラでは **OS そのものが設定対象** になる:

- `sudo systemctl restart nginx` … OS のサービス管理機構 (systemd) を直接叩く
- `/etc/ssl/cds01.crt` を置く … OS のファイル配置慣例に従う
- `update-ca-certificates` … OS の「信頼する CA リスト」を更新する OS 提供のコマンド
- `chmod 600 cds01.key` … OS のファイル権限を設定する

これらは **アプリのコードからは普通操作しない**領域。アプリ層から見て「動く環境」だったものが、ここでは設定対象そのものになる。

## なぜインフラでは VM で分けるのか

アプリ層では「同じ Mac の上で別プロセス」でサーバ／クライアントを分けても、十分に学べる。なぜインフラ層では「別の OS（VM）」で分ける必要があるのか:

- **攻撃者は別マシンから来る** ので、同じプロセス内のループバックで再現しても意味がない
- **障害は片方のマシンだけで起きる** ので、サーバとクライアントは別の OS にいないと再現性がない
- **負荷分散・冗長化** はそもそも「複数のマシン」が前提
- **OS 設定の差** （カーネル設定、systemd ユニット、証明書ストア、ファイアウォール）は VM 単位でしか試せない

つまり「サーバとクライアントが別の OS に分かれている状態そのもの」が、インフラ層では学習対象になる。

## レイアの俯瞰

```
[ ユーザー / ブラウザ ]
        |
[ アプリ層 ]                    ← http-from-scratch, security-lessons (前半)
   - HTTP リクエスト/レスポンス
   - XSS, CSRF, SQLi
   - JS, Python, Ruby のアプリコード
        |
[ 認証・認可層 ]                 ← security-lessons (中盤・予定)
   - パスワード保存, JWT, OAuth
        |
[ Web サーバ / アプリサーバ ]    ← infra-lessons (現在地)
   - nginx, systemd, OS の設定
   - サーバ証明書 (TLS)
        |
[ サプライチェーン / 配信 ]      ← infra-lessons/01-package-delivery
   - パッケージ署名 (GPG)
   - クライアント証明書認証 (mTLS)
   - リポジトリ配信
        |
[ ネットワーク / OS / カーネル ]
   - /etc/hosts, ファイアウォール
   - TCP/IP スタック
        |
[ ハードウェア / 仮想化 ]
   - VM (Multipass)
   - 物理サーバ
```

同じ単語（例: TLS, サーバ）が複数の段に出てくるが、それぞれの段で「実体」が違う。`http-from-scratch` の TLS と `infra-lessons` の TLS は、抽象としては同じ仕組みだが、**触れている層が違う**。

## 行き来するときの判断軸

| 「やりたいこと」 | どのプロジェクト |
|---|---|
| HTTP プロトコルの中身を理解したい | http-from-scratch |
| Web アプリの脆弱性を再現したい | security-lessons |
| 認証・JWT を扱いたい | security-lessons (03-auth 予定) |
| パッチ配信・パッケージ署名・サプライチェーンを扱いたい | infra-lessons/01-package-delivery |
| ロードバランサ・冗長化・IaC を扱いたい | infra-lessons (今後の層) |

「サーバを立てたい」だけだと曖昧。**どのレイアの「サーバ」か** を意識すると、どのプロジェクトで学ぶべきかが決まる。
